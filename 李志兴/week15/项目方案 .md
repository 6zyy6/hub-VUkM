# 项目方案：多模态 RAG 问答系统

## 1. 项目目标

开发一个单人本地使用的通用多模态 RAG 问答系统。

系统用于对用户上传的多类型资料进行解析、入库、检索、重排和问答生成。

系统必须支持答案来源引用、原文回看、PDF 定位高亮、图片来源查看和表格来源查看。

本文件作为项目开发的唯一方案依据。

## 2. 协作与方案维护规则

1. 本文件作为唯一项目方案源文件。
2. 已确认需求、设计、约束写入本文档。
3. 文档按结构化章节维护，不进行无序追加。
4. 文档中不保留相互冲突的方案。
5. 文档中不写入未确认的猜测性内容。
6. 其他 AI 或开发人员必须优先依据本文档生成代码。
7. 新增功能必须先更新项目方案，再修改代码。

## 3. 第一版系统范围

系统类型：多模态 RAG 问答系统。

使用场景：通用场景，不绑定具体行业。

使用模式：单人使用。

知识库模式：支持多个知识库。

问答范围：每次问答只能选择一个知识库。

提问方式：第一版只支持文字提问。

上传资料：支持 MinerU 可解析的文件类型。

答案生成：采用严格 RAG 模式。

部署方式：Docker Compose 本地部署。

## 4. 第一版不实现的功能

1. 多用户账号体系。
2. 注册、登录、密码认证和会话鉴权。
3. 组织空间。
4. 用户间知识库隔离。
5. 跨知识库联合检索。
6. 知识库内文件夹、目录、标签和文件移动。
7. 基于历史消息的连续追问。
8. 上传图片作为问题的一部分。
9. 云数据库、云对象存储和云消息队列。
10. Kubernetes 部署。
11. MinerU 官方 API 接入。
12. 每个知识库单独创建 Milvus Collection。
13. 模型服务纳入主 Docker Compose。

## 5. 技术栈

### 5.1 后端

后端框架：Python FastAPI。

接口风格：REST API。

流式输出：Server-Sent Events。

API 文档：FastAPI 自动生成 OpenAPI 文档。

数据库迁移：Alembic。

### 5.2 前端

前端框架：React。

开发语言：TypeScript。

构建工具：Vite。

组件库：Ant Design。

### 5.3 数据与基础设施

关系型数据库：PostgreSQL。

向量数据库：Milvus。

消息队列：Kafka。

文档解析：本地部署 MinerU。

文件存储：本地文件存储。

部署编排：Docker Compose。

### 5.4 模型服务

问答生成模型：Qwen-VL 系列多模态模型。

Embedding 模型：可配置 HTTP 接口，默认本地 embedding 服务。

Reranker 模型：可配置 HTTP 接口，默认本地 reranker 服务。

Qwen-VL、embedding、reranker 第一版作为外部可配置 HTTP 服务接入，不纳入主 `docker-compose.yml`。

## 6. 系统总体架构

系统模块包括：

1. 前端 Web 应用。
2. FastAPI 后端服务。
3. Kafka 文件处理任务队列。
4. 文件处理 Worker。
5. 本地 MinerU 解析服务。
6. PostgreSQL 数据库。
7. Milvus 向量数据库。
8. 本地文件存储。
9. 外部 Qwen-VL 多模态问答服务。
10. 外部 embedding 服务。
11. 外部 reranker 服务。

主流程：

1. 用户创建或选择知识库。
2. 用户上传文件。
3. 后端保存原始文件并创建文件记录、任务记录。
4. 后端向 Kafka 写入文件处理任务。
5. Worker 消费任务。
6. Worker 调用 MinerU 完成文档解析。
7. Worker 基于 MinerU 解析结果进行结构优先切分。
8. Worker 调用 embedding 服务生成向量。
9. Worker 将向量写入 Milvus。
10. Worker 将内容块元数据写入 PostgreSQL。
11. 用户在选定知识库中发起文字提问。
12. 后端向量化问题。
13. 后端在 Milvus 中按 `knowledge_base_id` 过滤检索。
14. 后端调用 reranker 重排候选内容块。
15. 后端组装文本上下文和视觉上下文。
16. 后端调用 Qwen-VL 生成答案。
17. 后端通过 SSE 返回答案。
18. 前端展示答案和引用来源。
19. 用户点击引用后打开来源 Drawer。
20. 前端展示 PDF 高亮、图片来源、表格来源或内容块详情。

## 7. 文档解析范围

文档解析引擎：MinerU。

MinerU 接入方式：本地部署 MinerU 服务。

业务后端通过本地 HTTP API 调用 MinerU。

MinerU 作为独立服务部署，不与业务后端写在同一进程中。

第一版支持资料类型：

1. PDF。
2. 图片。
3. DOCX。
4. PPTX。
5. XLSX。

系统不为上述类型之外的文件单独开发解析器。

上传文件进入知识库前必须经过 MinerU 解析。

MinerU 解析结果作为后续切分、向量化、检索和问答生成的唯一文档内容来源。

第一版不接入 MinerU 官方 API。

## 8. 知识库与文件管理

知识库功能：

1. 创建知识库。
2. 查看知识库列表。
3. 切换当前知识库。
4. 重命名知识库。
5. 删除知识库。

文件管理规则：

1. 每个知识库内只支持文件列表管理。
2. 不支持文件夹。
3. 不支持目录。
4. 不支持标签。
5. 不支持文件移动。
6. 支持一次选择并上传多个文件。
7. 每个文件对应一个独立处理任务。
8. 文件上传成功后自动解析并构建索引。
9. 用户不需要手动点击解析或入库。

文件状态枚举：

1. `uploading`：上传中。
2. `pending_parse`：等待解析。
3. `parsing`：解析中。
4. `chunking`：切分中。
5. `embedding`：向量化中。
6. `indexing`：索引构建中。
7. `completed`：已完成。
8. `failed`：失败。

失败时前端显示失败状态和失败原因。

## 9. 文件处理任务

任务调度：后端使用 Kafka 处理文件入库流程。

任务粒度：每个文件对应一个独立处理任务。

任务步骤：

1. 上传保存。
2. MinerU 解析。
3. 内容切分。
4. 预览资源生成。
5. 向量化。
6. Milvus 索引写入。
7. PostgreSQL 状态更新。

Kafka Topic：

1. `rag_file_task`：文件处理主任务 Topic。
2. `rag_file_task_failed`：文件处理失败任务 Topic。

Kafka 消息只保存任务触发信息，不作为最终任务状态存储。

任务状态以 PostgreSQL 为准。

失败重试由 Worker 结合 PostgreSQL 中的任务状态和重试次数控制。

重试范围：解析、切分、预览资源生成、向量化、索引构建任一步骤失败后，均从失败步骤重新执行。

重试次数：每个失败步骤最多自动重试 3 次。

重试间隔：

1. 第 1 次重试间隔 10 秒。
2. 第 2 次重试间隔 30 秒。
3. 第 3 次重试间隔 60 秒。

3 次重试全部失败后，任务状态更新为 `failed`，并向 `rag_file_task_failed` 写入失败消息。

任务恢复：系统重启后，状态为 `pending_parse`、`parsing`、`chunking`、`embedding`、`indexing` 的任务重新进入任务队列。

并发配置：

1. MinerU 解析任务默认并发数为 1。
2. 向量化任务默认并发数为 2。
3. 索引写入任务默认并发数为 1。
4. 解析并发数、向量化并发数、索引写入并发数通过配置文件和环境变量配置。

## 10. 本地文件存储

第一版使用本地文件存储。

目录结构：

```text
storage/
  originals/
  parsed/
  previews/
  temp/
```

目录用途：

1. `storage/originals/` 保存原始文件。
2. `storage/parsed/` 保存 MinerU 解析产物。
3. `storage/previews/` 保存前端预览和高亮定位资源。
4. `storage/temp/` 保存临时文件。

删除知识库时，同步删除对应原始文件、解析产物、预览资源、数据库记录和向量索引。

## 11. 内容切分方案

文档切分方案：结构优先切分。

切分输入：MinerU 结构化解析结果。

切分对象：

1. 标题。
2. 正文段落。
3. 列表。
4. 表格。
5. 图片。
6. 图片说明。
7. OCR 文本。
8. 版面位置信息。

文本块规则：

1. 优先按标题、段落、列表等结构切分。
2. 超过 1200 tokens 的文本块继续切分。
3. 相邻文本块重叠 100 tokens。

表格块规则：

1. 表格独立成块。
2. 超过 50 行的表格按行切分。
3. 表格切分后保留表头。
4. XLSX 内容块保存工作表名称、行列范围和表格块编号。

图片块规则：

1. 图片说明、OCR 文本和相邻上下文合并为图片文本描述。
2. 图片文本描述用于向量召回。
3. 图片原图或裁剪图用于 Qwen-VL 多模态问答。

PDF 内容块规则：

1. 保存页码。
2. 保存版面坐标。
3. 保存块类型。
4. 保存原文文本。
5. 保存引用定位信息。

## 12. 多模态上下文规则

用户问题第一版只支持文字输入。

问答生成模型使用 Qwen-VL 系列多模态模型。

Qwen-VL 通过可配置多模态 Chat 接口调用。

Qwen-VL 接口支持文本内容和图片内容输入。

Qwen-VL 只接收最终入选的最多 8 个内容块中的相关图片资源。

Qwen-VL 不接收 Milvus 初始召回后但未进入最终上下文的图片资源。

文本上下文使用最终入选的最多 8 个内容块。

视觉资源规则：

1. PDF 中已被 MinerU 解析出的文字类内容直接作为文本上下文传入。
2. PDF 中的图片、图表、公式截图、复杂版面区域作为视觉资源传入。
3. PDF 视觉类内容有坐标时，优先传入裁剪区域图。
4. PDF 视觉类内容坐标缺失、坐标异常或裁剪失败时，传入整页截图。
5. 纯文本块不转换为截图。
6. 表格块不转换为截图。
7. 图片文件来源可传入原图或处理后的预览图。

## 13. PDF 预览与高亮

PDF 解析完成后生成每页预览图。

PDF 高亮定位使用 MinerU 返回的页码和版面坐标。

用户点击 PDF 引用时，前端打开对应页预览图。

前端按坐标在预览图上叠加高亮框。

PDF 中已解析出的文字类内容直接作为文本传给 Qwen-VL。

PDF 中图片、图表、公式截图、复杂版面区域按视觉资源规则生成裁剪图或整页截图。

## 14. 向量化方案

向量化模型采用可配置接口。

第一版优先支持 OpenAI-compatible Embeddings API。

默认使用本地 embedding 服务。

配置项包括：

1. 服务地址。
2. 模型名称。
3. API Key。
4. 向量维度。
5. 批处理大小。
6. 超时时间。

更换 embedding 模型或向量维度后，已有知识库必须重新向量化并重建索引。

## 15. Milvus 向量库设计

向量数据库：Milvus。

部署方式：本地部署 Milvus 服务。

Collection 名称：`rag_document_chunks`。

Collection 设计：单 Collection。

知识库隔离方式：通过 `knowledge_base_id` 标量字段过滤。

第一版不为每个知识库单独创建 Collection。

第一版不使用 Milvus Partition 做知识库隔离。

每次检索必须添加 `knowledge_base_id` 过滤条件。

Milvus 只保存向量和检索必要元数据。

正文、引用定位、完整结构化元数据以 PostgreSQL 为准。

字段：

| 字段名 | 类型 | 说明 |
|---|---|---|
| id | VarChar | 向量记录 ID，对应 PostgreSQL 内容块向量 ID |
| chunk_id | VarChar | 内容块 ID |
| knowledge_base_id | VarChar | 知识库 ID |
| file_id | VarChar | 文件 ID |
| chunk_type | VarChar | 内容块类型 |
| page_number | Int64 | PDF 页码，无页码时为空 |
| embedding | FloatVector | 内容块向量 |
| created_at | Int64 | 创建时间戳 |

默认向量索引：HNSW。

默认相似度度量：COSINE。

默认索引参数：

1. `M=16`
2. `efConstruction=200`
3. `ef=64`

向量维度、索引类型、度量方式和索引参数从 `config/app.yaml` 读取。

后端启动时检查 Collection。

Collection 不存在时自动创建。

Collection 存在时进行结构校验。

校验失败时后端不得启动。

## 16. 检索与重排方案

检索方案：Milvus 向量召回 + 可配置 reranker 重排。

检索范围：当前选中的单个知识库。

所有检索请求必须按 `knowledge_base_id` 过滤。

用户问题使用当前配置的 embedding 模型向量化。

Milvus 初始召回数量：`top_k=30`。

Reranker 后保留数量：`top_n=8`。

最终进入大模型上下文的内容块最多 8 个。

Reranker 默认启用，支持关闭。

Reranker 输入：用户问题和 Milvus 召回候选内容块。

Reranker 输出：内容块 ID 和相关性分数。

最终进入大模型上下文的内容块必须来自重排后的结果。

## 17. 问答生成方案

问答生成采用严格 RAG 模式。

答案必须基于检索到的内容块生成。

知识库依据不足时，必须明确说明：当前知识库中未找到足够依据。

不得使用模型自身知识补全答案。

不得编造文件名、页码、表格位置、图片来源和内容块编号。

问答接口必须支持 SSE 流式输出。

答案必须返回引用来源。

每条引用至少包含：

1. 知识库名称。
2. 文件名。
3. 内容块 ID。
4. 内容块类型。
5. 页码或表格位置。
6. 引用文本摘要。
7. 预览资源 ID。

检索不到可靠来源时，不得编造引用。

## 18. Prompt 模板管理

Prompt 模板采用外部模板文件管理。

模板目录：`config/prompts/`。

第一版模板：

1. `config/prompts/rag_answer.md`
2. `config/prompts/insufficient_context.md`

代码中不得硬编码 Prompt 正文。

系统启动时校验必需 Prompt 模板文件是否存在。

Prompt 模板修改后，后端重启生效。

## 19. 问答会话管理

第一版支持多个问答会话。

每个问答会话归属于一个知识库。

会话功能：

1. 创建会话。
2. 查看会话列表。
3. 切换会话。
4. 重命名会话。
5. 删除会话。

保存每个会话的历史消息。

消息保存内容：

1. 用户问题。
2. 模型答案。
3. 引用来源。
4. 检索内容块。
5. 模型配置快照。
6. 创建时间。

同一问答会话内不支持基于历史消息的连续追问。

每次用户提问均作为独立问题处理。

历史消息仅用于查看和追溯。

历史消息不参与问题改写、检索和答案生成。

删除知识库时，同步删除该知识库下的问答会话、历史消息和引用记录。

PostgreSQL 不保存向量数据。

PostgreSQL 保存 Milvus 向量 ID 和内容块元数据。

## 21. 模型服务接口规范

### 21.1 通用规则

模型服务通过 HTTP 调用。

模型服务地址、模型名称、API Key、超时时间和调用参数从配置文件读取。

支持 Bearer Token 鉴权。

调用失败时按错误码返回给后端统一异常处理。

### 21.2 Qwen-VL 多模态 Chat 接口

接口风格：OpenAI-compatible Chat Completions。

路径示例：`POST /v1/chat/completions`。

请求必须支持：

1. `model`
2. `messages`
3. `temperature`
4. `max_tokens`
5. `stream`
6. 文本输入。
7. 图片输入。

图片输入格式：base64 data URL。

Qwen-VL 响应支持流式输出。

后端将 Qwen-VL 流式响应转换为前端 SSE 事件。

### 21.3 Embedding 接口

接口风格：OpenAI-compatible Embeddings。

路径示例：`POST /v1/embeddings`。

请求字段：

1. `model`
2. `input`

响应字段必须包含向量数组。

后端校验向量维度。

向量维度与配置不一致时，入库流程失败。

### 21.4 Reranker 接口

路径示例：`POST /rerank`。

请求字段：

1. `query`
2. `documents`
3. `top_n`

`documents` 中每个元素包含：

1. `chunk_id`
2. `content`
3. `metadata`

响应字段：

1. `chunk_id`
2. `score`

Reranker 返回结果必须能映射到输入内容块。

Reranker 失败且配置为启用时，问答请求失败。

Reranker 配置为关闭时，直接使用 Milvus 召回排序结果。

### 21.5 模型服务检测接口

后端提供接口：`POST /api/v1/config/model-services/test`。

检测范围：

1. Qwen-VL 服务连通性。
2. Embedding 服务连通性。
3. Reranker 服务连通性。
4. Embedding 向量维度一致性。

## 29. 开发规范与代码约束

### 29.1 通用约束

1. 不得硬编码配置项。
2. 不得擅自增加未确认功能。
3. 不得绕过 `knowledge_base_id` 过滤进行检索。
4. 不得在日志中输出 API Key。
5. 不得在 PostgreSQL 中保存向量数据。
6. 不得在业务代码中硬编码 Prompt 正文。

### 29.2 后端分层

后端代码按 API、Schema、Service、Repository、Integration 分层。

API 层只处理请求、响应和参数校验。

Service 层处理业务流程。

Repository 层处理数据库读写。

Integration 层处理外部服务调用。

### 29.3 Worker 规范

Worker 必须以 PostgreSQL 任务状态为准。

Worker 处理每个步骤前必须检查任务当前状态。

Worker 每个步骤成功后必须更新任务状态。

Worker 每个步骤失败后必须记录错误码、错误信息和重试次数。

### 29.4 数据库规范

修改数据库表结构必须生成 Alembic 迁移。

删除知识库必须同步清理相关文件、任务、内容块、会话、消息、引用和向量索引。

### 29.5 前端规范

前端 API 类型必须统一定义。

前端不得直接拼接后端未定义接口。

前端错误展示必须使用后端返回的统一错误格式。

引用 Drawer 关闭不得清空问答状态。

## 30. 基础安全与数据边界

第一版为单人本地使用系统，不实现登录认证。

上传文件必须限制在 MinerU 支持类型内。

后端文件访问必须基于数据库记录和受控存储目录。

接口不得允许通过路径参数读取任意系统文件。

API Key 通过环境变量或本地配置注入，不提交到代码仓库。

日志不得输出 API Key、完整 Authorization Header 和模型服务密钥。

## 31. 测试方案

测试类型：

1. 单元测试。
2. 集成测试。
3. 端到端测试。
4. 失败重试测试。
5. 严格 RAG 测试。
6. 多模态测试。
7. 性能与稳定性测试。

必须覆盖主链路：

上传文件 → Kafka 任务 → MinerU 解析 → 切分 → 预览资源生成 → 向量化 → Milvus 入库 → 检索 → reranker → Qwen-VL → SSE 输出 → 引用来源 → PDF 高亮 / 图片预览 / 表格预览。

严格 RAG 测试要求：

1. 知识库有依据时，答案必须包含引用。
2. 知识库无依据时，答案必须说明当前知识库中未找到足够依据。
3. 答案不得编造来源。

失败重试测试要求：

1. MinerU 失败后重试。
2. Embedding 失败后重试。
3. Milvus 写入失败后重试。
4. 达到最大重试次数后进入失败状态。

多模态测试要求：

1. PDF 文字内容按文本进入上下文。
2. PDF 图表内容按裁剪图进入 Qwen-VL。
3. 裁剪失败时使用整页截图。
4. 图片文件可被检索并在引用中查看。
5. XLSX 表格可被检索并查看行列范围。

## 33. 第一版验收标准

1. 可以通过 Docker Compose 启动 PostgreSQL、Milvus、Kafka、MinerU、后端和前端。
2. 可以创建、重命名、删除多个知识库。
3. 每次问答只能选择一个知识库。
4. 可以上传 PDF、图片、DOCX、PPTX、XLSX。
5. 文件上传后自动进入处理流程。
6. 前端可以显示文件处理状态。
7. 失败任务可以自动重试。
8. 文件解析结果可以切分并写入 Milvus。
9. 用户可以在知识库中发起文字提问。
10. 系统可以完成向量召回和 reranker 重排。
11. 系统可以调用 Qwen-VL 生成严格 RAG 答案。
12. 答案必须包含可点击引用来源。
13. 点击 PDF 引用后可以打开对应页并高亮相关区域。
14. 点击图片引用后可以查看图片来源。
15. 点击表格引用后可以查看工作表、行列范围和表格预览。
16. 知识库依据不足时，系统不得编造答案和引用。
17. 历史消息可查看，但不参与后续问答。
18. 模型服务地址和参数可通过配置文件管理。
19. API Key 不硬编码在代码中。
20. 项目文档足以指导其他 AI 或开发人员完成第一版开发。
